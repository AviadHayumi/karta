part 1 · usage

start with a question jq answers wrong

a cronjob's status.active is a list of job references , not a count. ask "is something active ?" the naive way :
jq 
# active = [ {kind: Job, name: ...} ]
.status.active > 0

# jq has a total order over ALL values.
# a list is always "bigger" than a number.
# => true. always. even when the list
#    shape is not what you meant.
cel 
# same field , same question
object.status.active > 0

# ERROR: found no matching overload
# for '_>_' (list, int)

# cel refuses to invent an answer.
# a loud typed error at evaluation -
# not a silently wrong status.
jq answers Running→ even when the shape is wrong
cel answers no matching overload→ you fix the expression , not the incident
real test : pkg/cel/evaluator_test.go · "rejects comparing a list to a number"
part 1 · usage

the same read , two spellings

every definition binds the workload as one document. jq walks it with paths , cel with member access. the real difference is what happens when a field is missing.
jq · docs/catalog on main 
specDefinition:
  podTemplateSpecPath: .spec.jobTemplate.spec.template

# a missing field just yields null mid-path.
# convenient - and silent.
cel · v1alpha2 · docs/catalog 
specDefinition:
  podTemplateSpec:
    expression: object[?"spec"][?"jobTemplate"][?"spec"][?"template"].orValue(null)

# plain access on a missing field is an error.
# [?"k"] makes absence a VALUE you handle,
# .orValue(null) says what it becomes.
jq .a.b.c · absence is implicit cel object[?"a"][?"b"].orValue(null) · absence is explicit rule every optional hop is spelled out smallest one core-pod : read object · one MergePatch entry : value
part 1 · usage

defaults : // vs orValue , and the false trap

jq's // falls through on null and on false. cel's orValue only fires on absence. one catalog line kept us honest :
jq · lws group key on main 
groupByKeyPaths:
  - .metadata.labels["…/group-index"] // "0"

# label missing        -> "0"   ok
# but if a value were false -> "0" too.
# // cannot tell false from absent.
cel · v1alpha2 · same key 
groupByExpressions:
  - ([dyn(object[?"metadata"][?"labels"]["…/group-index"]
      .orValue(null))]
      .filter(v, v != null && v != false)
      + ["0"])[0]

# the coalesce idiom : first value that is
# neither null nor false , else the default.
# faithful to what jq did , stated in full.
the takeaway : cel makes you say which values count as "missing". jq decided for you , and false was one of them.
part 1 · usage

streams vs lists : how many things did i just read ?

jq expressions yield a stream - zero , one , or many outputs. cel yields exactly one value. instanced components need many , so cel returns a list and the engine spreads it.
jq · jobset instances on main 
instanceIdPath: .spec.replicatedJobs[].name

# [] iterates : one output per job.
# "master" , "worker" arrive as a stream.
cel · v1alpha2 · same read 
instanceIDs:
  expression: >-
    …replicatedJobs…[0].map(x,
      x[?"name"].orValue(null))

# map builds ONE list : ["master","worker"].
# the runner spreads a list result into the
# stream shape callers already expect.
jq .[] = many results cel .map(x, …) = one list bridge pkg/cel/runner.go : a list result is spread , one entry per element
part 1 · usage

pipes become comprehensions

jq composes with | stages. cel composes with macros over collections - the same vocabulary kubernetes uses in crd validation rules.
jq · "is a Ready condition true ?" 
.status.conditions[]
  | select(.type == "Ready")
  | .status == "True"

# read left to right :
# iterate , keep some , test each.
cel · the same question 
object.status.conditions.exists(c,
  c.type == "Ready" && c.status == "True")

# one macro , one boolean.
# also available : .all() .filter() .map()
# - the vocabulary of k8s CEL everywhere.
select → filter / exists any / all → exists / all length > 0 → .size() > 0 to_entries[].key → .map(k, string(k)).sort()
part 1 · usage · the big one

writes : the read path is no longer the write path

in jq , the read expression doubled as an l-value : the engine wrote through it. a cel expression is a computation - it has no address. so writes became their own thing : a patches list , the shape MutatingAdmissionPolicy uses for its mutations.
jq · v1alpha1 · suspend a cronjob 
suspendActions:
  - path: .spec.suspend
    value: "true"

# engine side (pkg/jq/execution/runner.go):
#   (.spec.suspend) = $val
# the path IS the location.
cel · v1alpha2 · same action 
suspendActions:
  - patchType: MergePatch
    expression: '{"spec": {"suspend": true}}'

# an entry declares what it builds :
#  MergePatch -> a map , applied as a
#    JSON merge patch (null deletes)
#  JSONPatch  -> a list of RFC 6902 ops
# one patch = a list with one entry.
podTemplateSpec:
  expression: …map(x, x[?"template"][?"spec"][?"template"]…)
  patches:
    - patchType: JSONPatch
      expression: '[{"op": "add",
        "path": "/spec/replicatedJobs/" + string(index)
                + "/template/spec/template",
        "value": value}]'

◆ what an entry can see

value - the value karta is writing
index - list-keyed instances : "/spec/replicatedJobs/" + string(index)
instance - map-keyed instances : {"services": {instance: {…}}} (dynamo)
variables.<name> - the definition's named expressions
patchStrategy: Replace - clear first , then set (two passes)

part 1 · usage

conditional writes : first match wins

sometimes the right patch depends on the document - a cronjob keeps its template under spec.jobTemplate , a deployment under spec. entries take match conditions ; the first entry whose conditions hold supplies the patch.
kep-0001 · a shape-dependent write 
patches:
  - matchConditions:
      - name: has-job-template
        expression: object.?spec.?jobTemplate.hasValue()
    patchType: MergePatch
    expression: '{"spec": {"jobTemplate":
      {"spec": {"template": value}}}}'
  - patchType: MergePatch
    expression: '{"spec": {"template": value}}'

# no conditions = always matches : the
# else entry. it may only appear last.

◆ errors never mean false

a condition must return a cel boolean. an error , a null , or a non-boolean is a failed write , not a false. and if nothing matches , the write fails loudly - the definition said nothing about this shape , and guessing is what got removed.

◆ the upstream vocabulary

matchConditions with a required name is how admission policies gate on cel. the name makes failures addressable : "condition has-job-template failed" , not "condition 0 failed".

◆ control flow in the api

the same branch as a ternary inside one expression is legal cel - but that smuggles a mini-language into a string. the branching lives in the patches list , where a reviewer and a validator can see it.

part 1 · usage

one karta , both spellings , side by side

jobset's running rule - the whole difference in one screen. same meaning , different honesty about absence and types.
jq · v1alpha1 · docs/catalog/jobset-… 
running:
  - byExpression:
      expression: >-
        (.status.replicatedJobsStatus // [])
        | any(.ready > 0 and .active > 0)
          and all(.failed == 0)
      expectedResult: "true"
cel · v1alpha2 · docs/catalog/jobset-… 
running:
  - byExpression:
      expression: >-
        …replicatedJobsStatus…[0].exists(r,
          r.?ready.orValue(0) > 0 &&
          r.?active.orValue(0) > 0)
        && …[0].all(r, r.?failed.orValue(0) == 0)

# no expectedResult. a byExpression is a
# boolean now , like every k8s cel gate.
longer ? yes. every .orValue(0) is a decision jq made silently and each default is written where a reviewer can see it expectedResult is gone - comparing a stringified bool to "true" was a jq leftover
part 1 · usage

variables : name the expression once

the coalesce idiom is verbose , so a definition names it once at spec level and reuses it everywhere - exactly how a ValidatingAdmissionPolicy composes its expressions.
docs/catalog/leaderworkerset-…-v1.yaml 
variables:
  - name: specReplicas
    expression: ([dyn(object[?"spec"][?"replicas"]
      .orValue(null))].filter(v,
      v != null && v != false) + [1])[0]
  - name: specLeaderWorkerTemplateSize
    expression: ([dyn(object.?spec.?leaderWorkerTemplate
      .?size.orValue(null))].filter(v,
      v != null && v != false) + [1.0])[0]

◆ used as

variables.specReplicas in any expression or patch of the definition. evaluated in order , later ones can reference earlier ones.

◆ the lws worker total

variables.specReplicasFloat * (variables.specLeaderWorkerTemplateSize - 1.0) - a computed scale no single path could express.

◆ resolved lazily

only the variables an expression syntactically references - transitively - get evaluated , so one broken variable cannot poison an expression that never mentions it. dynamic access like variables[x] falls back to resolving all of them.

part 1 · usage · design , not shipped yet

references : reading beyond the workload

some workloads keep half their spec in another object. a trainjob points at a clustertrainingruntime that holds the base pod template - the definition alone never sees it. the references design fixes that : a named pointer to another resource , declared on the structure , resolved by the consumer.
references · reserved for its own kep 
references:
  # single object: references.trainingRuntime
  - name: trainingRuntime
    apiVersion: trainer.kubeflow.org/v1alpha1
    kind: ClusterTrainingRuntime
    lookup:
      nameExpression: object.spec.runtimeRef.name

  # set of objects: references.pods
  - name: pods
    apiVersion: v1
    kind: Pod
    list:
      selector:
        matchLabelExpressions:
          - key: training.kubeflow.org/job-name
            expression: object.metadata.name

◆ two shapes

lookup - one object , read like any object. list - a set , iterated with the comprehension macros , possibly empty.

◆ karta stays declarative

karta fetches nothing itself. the consumer resolves the references and passes the values in - one more input , like a ValidatingAdmissionPolicy gets its params.

◆ bounded by construction

required by use : a lookup that finds nothing only fails the expressions that mention it. and there is no namespace field - a definition can never reach outside the workload's namespace.

part 1 · usage · design , not shipped yet

and cel reads a reference like any other input

no new syntax. a reference is just another bound name , so the override-with-fallback read and the aggregate-over-pods status both come out as ordinary cel.

  image:
    expression: >-
      object.?spec.?trainer.?image.orValue(
        references.trainingRuntime.spec.template
          .spec.replicatedJobs[0].template.spec
          .template.spec.containers[0].image)

# prefer the trainjob's value ,
# fall back to the runtime's base.

part 2 · internals

the contract : resource code never meets the engine

the resource layer talks to an interface. the factory builds one runner per workload , binds the definition's variables , and hands it over. a broken build becomes an errRunner - every call reports the construction error instead of guessing.
type Runner interface {
    Evaluator          // Evaluate, GetObject
    Assigner           // Assign - root only,
                       // writes go through patches
    VariableEvaluator  // EvaluateWithVariables,
                       // ResolveVariables
}
func NewComponentFactoryFromObject(karta *v1alpha1.Karta,
    object KubernetesObject) *ComponentFactory {
  celRunner, err := celpkg.NewRunnerWithVariables(
      object, namedExpressions(karta))
  if err != nil {
    return NewComponentFactory(karta,
        NewAccessor(errRunner{err}))
  }
  return NewComponentFactory(karta,
      NewAccessor(celRunner))
}
a runner is bound to one document Assign exists for exactly one location : the root , after a patch is applied mocks generated from the contract , not from an engine

part 3 · the version bump

breaking the crd anyway - so go upstream

cel breaks the crd , and a breaking version is the one cheap moment to fix names and shapes that drifted from how kubernetes does things. every change in kep-0001 stands on a shipping upstream precedent :

◆ scheduling , not one consumer

optimizationInstructions → scheduling (the RuntimeClass.spec.scheduling name) , and the singular podGroup with subGroups replaces the already-deprecated plural.

◆ apiVersion + kind

kind: {group, version, kind} → the two lines every manifest starts with. no user-facing k8s api nests a gvk struct , and kind.kind stops stuttering.

◆ booleans , not strings

byExpression.expectedResult is gone. every cel gate upstream - validations , matchConditions , crd rules - is a bare boolean.

◆ instanceIDs

instanceIdPath → instanceIDs. upstream spells machineID , systemUUID , providerIDList - there is no Ids anywhere in its api types.

◆ keys that cannot collide

additionalChildKinds entries flatten too , and the list key becomes (apiVersion , kind) - kind alone collides across groups.

◆ the admission vocabulary

patches , matchConditions , variables , expression - byte for byte the words an admission-policy author already knows.

the whole proposal , with before / after for every field : keps/0001-cel-expressions on the kep-cel branch
the payoff

what you actually get

◆ the k8s language

the same cel that powers crd validation rules and admission policies. an author who writes a ValidatingAdmissionPolicy already knows karta.

◆ typed refusals

list-vs-number , string-vs-bool - wrong questions fail loudly with a typed error , never as a silently wrong status in production.

◆ reads never write

an expression is a computation. the write is a patch you can read , review , and reason about - like a MutatingAdmissionPolicy.

◆ writes land whole

every patch is built against the pre-write document , then applied all-or-nothing with a snapshot rollback.

◆ bounded by design

no recursion , no unbounded builtins , a cost budget on every evaluation. a definition is data you can afford to run.

◆ the api did not move

accessor , component , factory , tree - consumers recompile without noticing. only definitions changed spelling.

the definition is data . the engine is bounded . reads are expressions , writes are patches .
